# 一、strategy.md(策略本体)的问题

**1. VWAP 没有按交易日重置,这是最致命的一个逻辑漏洞。**
文档自己也承认了。VWAP 的本质是"今天从开盘到现在的成交量加权均价",如果 `intraday` 窗口跨越多个交易日累计计算,VWAP 会被前几天的数据污染,完全失去作为日内锚点的意义。pullback/reclaim/momentum 三个核心信号全部依赖这个 VWAP,这个 bug 不修,后面所有回测结果都不可信。

**2. 信号产生和成交建模用的是同一根 K 线的收盘价(`modeled_current_close`)。**
这是经典的前视偏差(look-ahead bias)。逻辑上,你只有在这根 K 线收盘之后才能拿到它的 close 去算 VWAP、判断趋势、生成信号;但你不可能在"刚刚收盘的瞬间"就以这个收盘价成交——下单到成交之间至少有一根 K 线的延迟。正确做法是信号在 bar N 收盘后生成,成交价用 bar N+1 的开盘价(或更保守地用 N+1 的 VWAP/中间价)。当前做法会系统性地高估策略表现,尤其是在回踩反弹这类"价格刚好在这根 K 线收盘时转折"的场景里,虚高最严重。

**3. 没有最大加仓层数上限。**
止盈阈值表给到"3层及以上",但没看到任何 `max_layers` 参数。当前唯一的硬约束是 T 仓现金耗尽(`max_t_bucket`),这意味着层数上限是"被动地由资金决定",不是"主动设计的风险控制"。这是典型的网格/摊大饼(martingale-style averaging down)结构性风险——在单边下跌行情里,策略会越跌越买,直到弹药耗尽,而触发止损是按**均价**计算的,均价会跟着每次加仓持续下移,实际最大浮亏会比"止损3.5%"这个数字给人的直觉大得多。建议显式加 `max_layers`,并单独测算"全部层数打满后,价格再跌X%时的账户级最大回撤"。

**4. 退出阈值不随波动率(ATR)调整,但入场阈值要求 ATR。**
入场时 neutral 趋势要求 `daily_atr >= 1.8%`,但止盈止损(1.8%/1.4%/1.0%、止损3.5%)是固定数字,不区分标的当前波动率状态。SPCX(波动大)和 NVDA(波动相对小)用同一套止盈止损,大概率一个经常被打止损洗出去,另一个止盈空间又留得太保守。建议把止盈止损也换成 ATR 的倍数,而不是固定百分比。

**5. confidence 字段算了但没有被使用。**
策略算出了 0.0~0.9 的置信度,但下单金额永远是固定的 350 或 175,跟 confidence 完全无关。这意味着"高确信度信号"和"低确信度信号"用一样的仓位,白白浪费了一个本可以用来做仓位管理的信号。

**6. 标的组合(SPCX/TSLA/NVDA/MU/CPOX)缺少相关性/集中度控制。**
全局 T 仓上限是简单线性求和后 `min(..., 15000*0.3)`,完全没考虑这几个标的在科技股大跌时高度同向。组合层面的尾部风险没有被建模,极端情况下"5个独立账户各自风险可控"加总起来可能是"一次系统性下跌同时打穿5个止损"。

**7. T+0/T+1结算与PDT规则完全没有出现在文档里,这是合规层面的硬伤。**
策略本质是"当天/极短周期内反复买卖同一标的"的做T策略,这套打法是从 A 股"core+T"思路移植过来的。但要注意两个市场规则完全不同:

* A 股是 T+1 结算,当天买入的股票当天不能卖出(除非你本来就持有底仓、用底仓做"正T"卖出再低位买回)。如果未来真要在 A 股落地"先买后卖"的反T,在当天买入的部分根本卖不出去,这个策略的执行假设在 A 股市场不成立。
* 美股(TSLA/NVDA/MU/CPOX/SPCX 都是美股代码)允许 T+0,但受 FINRA Pattern Day Trader 规则约束:保证金账户净值低于 2.5 万美元、5个交易日内有4次以上日内交易,会被标记限制交易。当前每个标的的起始资金大约只有 3000 美元(15000/5),如果策略频繁触发 OPEN_T→CLOSE_T 的当日往返,现实中很可能直接撞上 PDT 限制,或者用现金账户的话会反复触发 Good Faith Violation(资金未结算就再次买入)。

这个问题不解决,前面所有回测数值在监管层面都是"实验室结果",不代表能真实执行。需要在文档里明确:目标账户类型(保证金 vs 现金)、目标市场(A股 vs 美股)、对应的结算和交易频率约束,再倒推策略允许的最小交易间隔。

**8. 没有隔夜跳空风险建模。**
1分钟异常波动检测(`flash_crash_pct=5%`)只能捕捉日内,捕不到隔夜跳空(比如财报后开盘跳空 -10%)。止损是按收盘价模型算的,但真实情况下隔夜跳空会导致止损成交价远差于模型假设的"current.close ± slippage_bps"。CPOX 这种盘子小的标的尤其容易跳空。

# 二、execution.md(执行层)的问题

**1. Paper 买入手续费被扣了两次,文档自己点名了这是 bug。**
`cash -= quote + fee`,但 `qty = (quote - fee) / price`——fee 既从买入数量里扣了一次,又额外从现金里扣了一次。这不是"口径选择"问题,是会让回测里的手续费成本被系统性放大,必须修。建议:先确定唯一口径(通常是 `cash -= quote`,`qty = (quote - fee) / price`,fee 已经隐含在数量里;或者 `cash -= quote + fee`,`qty = quote / price`),改完后补一条回归测试锁定这个行为。

**2. 多标的回测只持久化第一个标的的完整明细(trades/equityCurve/orderIntents/riskEvents)。**
这意味着你现在没办法审计"第二、第三个标的为什么在某天被拒绝下单",而风险事件审计恰恰是判断策略能不能上实盘最关键的材料。这个限制必须在接入更严格的策略验证流程之前解决,否则你看到的 summary 是聚合的,但聚合数字背后哪个标的贡献了亏损、哪个标的的风控生效了,完全是黑盒。

**3. 手工 Paper 下单不走 `RiskLimits` 检查。**
回测引擎有完整的点差/数据新鲜度/日内最大亏损/单笔限额/T仓上限检查,但 quick trade 手动下单完全绕过了这些。这会导致"策略本身很守规矩,但人工操作的 paper 单可以无限制下"——如果未来把 quick trade 直接对接到真实下单接口,这是一个完全没有风控的旁路入口,优先级很高。

**4. 数据源和标的不匹配:Binance 数据源拿不到美股代码。**
TSLA/NVDA/MU/CPOX/SPCX 是纳斯达克/纽交所股票,Binance 是加密货币现货交易所,公开 K 线接口里不会有这些股票代码的数据(除非未来接入的是某种代币化股票产品,但文档里没提)。目前 HTTP 层真正能跑的只有 Synthetic(假数据)。这意味着现在所谓的"回测",绝大多数场景下其实是在合成数据上调参——合成数据生成器(`generate_synthetic_spcx`)的统计特性和真实市场几乎不可能一致,在合成数据上调出来的 15 个以上的参数,对真实行情没有任何保证的迁移性。CSV 数据源代码可用但 HTTP 没暴露路径参数,等于唯一能接入真实历史数据的通道目前是"半成品"。这是上线前必须优先打通的基础设施缺口。

**5. 核心仓(70%)从未被实际建模,回测的"总收益"只反映T仓部分。**
文档写得很清楚:"核心仓...回测引擎不会买卖这部分"。这意味着 `ending_equity`、`totalReturnPct` 这些指标完全不包含占资金 70% 的核心仓在这段时间里自身涨跌带来的盈亏。如果产品定位是"评估核心+T这个组合打法相对于纯持有的增量价值",现在的回测根本回答不了这个问题——你看到的"回测收益率"和"如果我什么都不做只是持有"之间没有可比的基准。建议至少新增一个指标:`coreOnlyReturnPct`(核心仓单独按 close-to-close 计算的回报),以及 `strategyVsCoreOnlyAlpha`,否则没法证明这套"做T"动作到底是不是在创造正收益,还是在为手续费和滑点买单。

**6. 没有用户/权限/审计/幂等下单。**
这些文档自己也列为已知边界,但要强调:这些不是"锦上添花"的功能,是从 paper 走向任何形式的真实资金之前的硬性前提,尤其是幂等下单(防止网络重试导致重复下单)和审计日志(出问题后要能复盘是谁的请求、什么时间、什么参数导致的)。

# 三、frontend.md 的问题(偏产品/方法论,不是 UI 美观问题)

**1. "智能调参"和"压力测试"两个 tab 的数据来源是 `/api/state/static`,即静态/模拟数据,而不是真实跑出来的参数敏感度分析或情景压测。**
这是一个诚实性问题:UI 文案会让使用者误以为系统已经具备参数敏感度分析和压力测试能力,但实际上目前后端没有真正计算这些东西。在策略验证流程里,这两项恰恰是判断"参数是不是过拟合"的核心工具,如果长期停留在占位状态,使用者很容易对一个还没被验证过的策略产生虚假的信心。

**2. `sampleSplit`(样本区间/训练测试集划分)在前端有 UI,但后端完全没用。**
这意味着目前没有任何 in-sample / out-of-sample 的区分机制。15+ 个自由参数在没有样本外验证的情况下调出来的"好看的回测曲线",绝大概率是过拟合的结果。

# 四、从现在的状态到"可以真正用于实盘"需要走的标准流程

按风险递增的顺序排列,每一步都应该有明确的"通过/不通过"标准,前一步不过就不进入下一步。

**阶段0:策略假设的可解释性审查**
明确这套"VWAP回踩/动量+核心仓做T"策略的经济学/微观结构理由是什么——是赚谁的钱(短期均值回归还是趋势延续)、预期在什么市场状态下有效、什么状态下会失效(比如低波动盘整期、单边趋势期、流动性枯竭期)。如果说不清楚"为什么这个信号有边际优势",后面的回测数字再好看都不该当真。

**阶段1:数据基础设施**

* 接入真实的、经过拆股/分红调整、无生存者偏差的历史数据源(目前唯一可用的是合成数据,必须先解决)。
* 打通 CSV 真实历史数据的 HTTP 路径参数,或接入正规的美股数据供应商(如 Polygon、IEX、Alpaca、Tiingo 等),Binance 不适用于这批标的。
* 做数据质量检查:缺口、异常跳价、停牌、分红拆股事件。

**阶段2:回测引擎纠偏**

* 修复前视偏差(成交价改为下一根K线开盘,而不是当前K线收盘)。
* 修复手续费双重扣减的 bug。
* 修复多标的明细只保存第一个标的的问题,确保每个标的的 risk_events/trades 都能被审计。
* 补充核心仓的影子计价,产出"策略 vs 纯持有"的对比指标。

**阶段3:方法论意义上的"审查"**

* 样本内/样本外划分(把 `sampleSplit` 真正接通),至少做滚动窗口的 walk-forward 验证,而不是一次性在全部历史数据上调参后报一个总收益率。
* 参数敏感度分析:对 pullback_pct、stop_loss_pct、buy_grid_spacing_pct 等关键参数做 ±20%~30% 扰动,观察收益曲线是否平滑变化还是断崖式崩溃——崩溃说明这个参数附近是过拟合出来的"悬崖",不是稳健的边际。
* 跨标的、跨市场状态的稳健性测试:同一套参数分别在上涨/下跌/盘整、高波动/低波动的历史区间里跑,不能只看一段牛市区间的总收益。
* 交易成本敏感性测试:把滑点和点差假设分别调高 2x、3x,看策略的 alpha 是否还能覆盖成本——很多日内策略的"边际优势"本身就薄,稍微调高一点摩擦成本就转负。
* 用 Monte Carlo / bootstrap 对交易序列重采样,给出收益率和最大回撤的置信区间,而不是一个点估计。
* 用统计显著性的眼光看交易样本量:如果回测里某个标的全程只成交了十几次,任何收益率/胜率数字都没有统计意义。

**阶段4:风险框架补完**

* 把仓位规模从"固定金额(350/175)"改成与波动率/置信度联动的动态仓位法(比如 vol-targeting 或基于 confidence 的分级仓位)。
* 显式设置最大加仓层数和组合层面的相关性敞口上限。
* 把 `RiskLimits`(点差、数据新鲜度、日内最大亏损、单笔限额)统一应用到回测、手工 paper 下单、未来的真实下单三条路径上,不能只在回测里生效。
* 设计一个"一键平仓/熔断"的紧急开关,这是任何要接真实资金的系统的强制项,不是可选项。

**阶段5:合规与市场规则核查**

* 明确目标市场(A股 or 美股)和账户类型(现金账户 or 保证金账户),倒推这套"当日反复买卖"的执行假设在该市场是否成立(A股T+1结算下"先买后卖"不可行;美股要算清楚是否会撞上PDT)。
* 核查频繁短线交易对应的税务处理(美股的 wash sale 规则等)。
* 核查目标券商/交易所 API 的下单频率限制、最小报单间隔、是否支持你需要的订单类型。

**阶段6:真实数据下的纸面交易(不是合成数据)**

* 用真实的实时行情(不是 Synthetic)跑至少 1~3 个月的纸面交易,核心目的是验证:实盘延迟下信号生成是否还成立、真实成交价和回测假设的滑点模型偏差有多大、系统在真实网络/数据异常下是否稳定。
* 持续对比"纸面实际成交"与"回测模型预测的成交",量化模型偏差,反过来修正滑点/点差假设。

**阶段7:基础设施可用性**

* 订单管理要能处理部分成交、拒单、断网重试(必须幂等,防止重复下单)。
* 内部仓位台账要和券商真实账户做定期对账(reconciliation),不能只信自己的内存状态。
* 完整的操作日志和告警(风控触发、连续亏损、数据源失败要能第一时间通知人)。
* 密钥/凭证管理,沙盒环境和生产环境严格隔离。

**阶段8:分阶段真实资金投放**

* 先用远低于设计资金量的"冒烟测试"金额接入真实账户,验证下单链路本身没问题。
* 设定明确的暂停标准(比如实际回撤超过回测最大回撤的1.5倍、连续亏损天数超过历史分布的95分位)触发自动降级或人工介入,而不是等亏完了再复盘。
* 资金逐步爬坡,每次提高仓位规模前重新核对实际表现与预期(回测+纸面交易)的偏离程度。

**阶段9:持续治理**

* 任何参数或代码改动都要重新走一遍回测+纸面验证,不能直接改完就上线。
* 定期做策略衰减监控(market regime 是否变化、近期实际胜率/盈亏比是否系统性偏离历史)。
* 保留完整的版本和决策审计记录。

总结一句话:目前这套系统作为"研究和paper-only工作台"的产品形态是合理、克制的,文档里也反复强调了paper-only边界,这是好习惯。但如果终极目标是接入真实资金,现阶段最值得优先修的不是 UI,而是三个东西—— **VWAP不重置和前视偏差这两个会让回测数字失真的逻辑bug** 、 **核心仓收益从未被纳入评估导致没法证明策略真的有增量价值** 、 **T+0/PDT这类结算与合规约束完全没有进入设计** 。这三类问题不解决,后面调参调得再细,都是在一个不可信的地基上做精装修。
